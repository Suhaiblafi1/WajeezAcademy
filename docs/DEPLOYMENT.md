## ١) الواقع اليوم

| | |
|---|---|
| **النطاق** | `https://www.wajeezacademy.com` |
| **الاستضافة** | **Cloudways** |
| **النشر** | من GitHub تلقائيّا، بسكربتِ نشرٍ يبني على الخادم |
| **الـAPI** | **عمليّةُ Node** على الخادم نفسِه (خادم Fastify) |
| **الترويسات** | `public/.htaccess` — يُنسخ إلى `dist/` وقتَ البناء |
| **قاعدة البيانات** | PostgreSQL عبر `DATABASE_URL` |

### وما لم يعد صحيحا

- **`vercel.json` لا يُقرأ.** هو ملفُّ إعداداتٍ خاصٌّ بـVercel. وكلُّ ترويسةٍ فيه —
  سياسةُ المحتوى، وبصماتُ السكربتات، واستثناءُ عامل الخدمة — **لا أثرَ لها على
  Cloudways**. يبقى الملفُّ في المستودَع لأنّ اختباراتٍ تقرؤه وحاجزَ البصمات
  يحسبها عليه، وللرجوع إن لزم.
- **`api/index.js`** حزمةٌ مبنيّةٌ لدالّة Vercel السحابيّة. عمليّةُ Node على
  Cloudways تشغّل خادمَ Fastify مباشرةً، لا هذه الحزمة.
- **`deploy/`** (Docker + Caddy) تصميمٌ لخادمٍ ذاتيٍّ **لم يُستعمل قطّ**.
- **`.github/workflows/deploy.yml`** مكتوبٌ لخادمٍ ذاتيٍّ بـSSH، ولا يعمل تلقائيّا.

## ٢) ⚠️ ما يجب أن يفعله سكربتُ النشر — وأخطرُ ما في هذه الوثيقة

**`npm run build` وحدَه لا يكفي.** هو `tsc -b && vite build` — يبني الواجهةَ فقط.

وكان على Vercel سكربتٌ يفعل ستّةَ أشياءَ أخرى (`scripts/vercel-build.sh`)،
**وأربعةٌ منها مشروطةٌ بمتغيّرٍ اسمُه `VERCEL_ENV` — وهو غيرُ موجودٍ على
Cloudways**. فإن لم يُعوَّض عنها صراحةً في سكربت Cloudways، **فهي لا تعمل**:

| الخطوة | إن لم تعمل |
|---|---|
| `npx prisma generate` | البناءُ يفشل أو الأنواعُ تكذب |
| **`npx prisma migrate deploy`** | **انحرافُ مخطَّط**: ترحيلاتٌ جديدةٌ لا تُنفَّذ، فمساراتُ الخادم تسقط بـ٥٠٠ على أعمدةٍ غيرِ موجودة |
| `npm run build` | — |
| **`npm run catalog:import`** | **الكتالوجُ الذي يراه المتعلّمُ مجمَّد.** `‎/api/public/core-catalog` يقرأ **الجداولَ الحيّة**، والاستيرادُ هو ما يكتب فيها مسارات المستودَع ودوراتِه ومتونَه. فتصل شيفرةٌ جديدةٌ فوق **محتوًى قديمٍ لا يتغيّر** |
| **`npm run catalog:publish`** | **محرّكُ التشخيص مجمَّد** على لقطته القديمة — أسئلتُه وتوصياتُه |
| `node scripts/bundle-api.mjs` | لازمٌ لمسار Vercel وحدَه — لا حاجةَ له مع عمليّة Node |

> **وهذا احتمالٌ قائمٌ لم يُتحقَّق منه بعد** لشكوى «الموقعُ القديمُ يتصدّر»:
> الواجهةُ تتحدّث والمحتوى لا. **يُحسم بالخطوة الأولى في القسم ٤.**

### سكربتُ النشر المقترَح على Cloudways

```bash
set -e
npm ci
npx prisma generate
npx prisma migrate deploy          # لا يُشترط بأيّ متغيّرِ بيئة
npm run build                      # ويقرأ VITE_SITE_ORIGIN من البيئة
                                   # ويكتب ختمَ البناء تلقائيا (خطّاف prebuild)
CATALOG_IMPORT_SKIP_MIGRATE=1 npm run catalog:import
npm run catalog:publish
supervisorctl restart all          # ← ⚠️ بلا هذا لا يتغيّر الـAPI أبدا
# ثمّ: تفريغُ Varnish
```

> ## ⚠️ الخطوةُ التي تُنسى — وقد وقعت فعلا
>
> **عمليّةُ Node تبقى في الذاكرة بالشيفرة التي أقلعت بها.** فسحبُ GitHub يجري،
> و`npm run build` يجري، وملفّاتُ الواجهة تتغيّر على القرص — **والعمليّةُ
> العاملةُ لا تعلم بشيء**. وهي التي تخدم الكتالوجَ والأسعارَ والتشخيصَ
> والبوّابات.
>
> **وعلامتُه في الشاشة:** الواجهةُ تعرض الجديدَ والـ`‎/api/version` يعرض
> القديم. رُصد على هذه المنصّة بعينها: صفحةُ الدورات عرضت الإصلاحَ الجديد
> (٨١ دورةً بدل ٤) و`‎/api/version` ظلّ يردّ بشيفرةٍ سابقةٍ للدمج — ردّا
> **حيّا** لا مخزَّنا (حقلُ `الوقت` يتحرّك مع كلّ طلب)، فسقط Varnish من
> الاتّهام وبقيت العمليّة.
>
> **وزرُّ «إعادة تشغيل التطبيق» في لوحة Cloudways لا يكفي**: يعيد خادمَ الويب
> (Apache/Nginx) ولا يمسّ عمليّةَ Node. المطلوبُ إعادةُ تشغيل **وظيفة
> Supervisor** التي تشغّلها — من `Application ← Supervisor Jobs`، أو
> `supervisorctl restart all` عبر SSH.

**ولا يُنسى تفريغُ Varnish** — Cloudways يشغّله افتراضا وهو يخزّن HTML، ويعلو على
`.htaccess`. وموضعُه سكربتُ النشر نفسُه فلا يُنسى بعدها.

### أمرُ التشغيل — وما تضعه في وظيفة Supervisor

```
npm start
```

وهو `tsx server/index.ts` — خادمُ Fastify نفسُه. **ولا يحتاج بناءً**: الشيفرةُ
تُقرأ من القرص عند الإقلاع، فيكفي `git pull` ثمّ إعادةُ تشغيلٍ ليتحدّث الـAPI.

| المتغيّر | ماذا يضبط |
|---|---|
| `API_PORT` | المنفذ — الافتراض `7101` |
| `API_HOST` | العنوان — الافتراض `127.0.0.1` (المغلق). اضبطه `0.0.0.0` **فقط** إن كان الوسيطُ العكسيّ في حاويةٍ أخرى |
| `DATABASE_URL` | إلزاميّ. **وبدونه يحاول الخادمُ تشغيل قاعدةٍ مدمجةٍ للتطوير** |

> **ولماذا وُضع الأمرُ في المستودَع:** لم يكن موجودا، فكانت وظيفةُ Supervisor
> تشغّل أمرا مكتوبا باليد **خارج** المستودَع — لا يعرفه أحدٌ ولا يراجعه أحدٌ
> ولا يتحدّث حين تتغيّر الشيفرة. ويحرسه `server/tests/ops/start-command.test.ts`،
> ومعه حارسٌ أهمُّ منه: **ألّا تكون في مسار الإقلاع حزمةُ تطوير**. وقد أمسك
> واحدةً عند كتابته — `embedded-postgres` كانت تُستورَد استيرادا ثابتا، فتثبيتٌ
> إنتاجيٌّ رشيق (`npm ci --omit=dev`) كان يُسقط الخادمَ عند أوّل سطر.

## ٣) متغيّرات البيئة

### إلزاميّةٌ وقتَ **البناء** (تُقرأ في الحزمة، لا وقتَ التشغيل)

| المتغيّر | لماذا |
|---|---|
| `VITE_SITE_ORIGIN=https://www.wajeezacademy.com` | يُحقَن في `canonical` و`og:url` و`og:image` و`sitemap.xml` و`robots.txt`. **والبوتاتُ تقرأ هذه الوسومَ ولا تشغّل React** — فبدونه تُعلن كلُّ صفحةٍ نطاقا غيرَ نطاقك |

> **والاحتياطيُّ صار النطاقَ الحيّ** (`src/application/site/origin.ts` و`vite.config.ts`،
> ويحرس تطابقَهما `src/tests/site-origin.test.ts`). فالنسيانُ لم يعد كارثة —
> **لكنّ الضبطَ الصريحَ هو الصواب**، وهو الوحيدُ الذي يصمد لو تغيّر النطاق.

### إلزاميّةٌ وقتَ **التشغيل**

| المتغيّر | لماذا |
|---|---|
| `DATABASE_URL` | القاعدة |
| `APP_URL=https://www.wajeezacademy.com` | عليه تُبنى **روابطُ البريد** (تأكيدُ الحساب · استعادةُ كلمة السرّ · دعوةُ الموظّف) **والعودةُ بعد الدفع**. وبدونه يسقط إلى `http://localhost:7100` — رسالةٌ تصل برابطٍ لا يفتح عند أحد. والكودُ يرفض تفعيلَ Stripe بدونه بسببٍ مكتوب |
| `STORAGE_SECRET` | إن غاب، يُشتقُّ مفتاحُ توقيع الروابط من `DATABASE_URL` — **فتغييرُ عنوان القاعدة يُبطل كلَّ رابطٍ موقَّعٍ صامتا** |
| `PAYMENT_*` | القسم ٥ |
| `RESEND_API_KEY` | القسم ٦ — **وجودُه وحدَه يفعّل قناةَ البريد** |

## ٤) كيف تعرف أنّ ما تراه هو الأحدث

**`‎/api/version` مفتوحٌ بلا مصادقة، وهو الجوابُ الوحيدُ الصادق:**

```
https://www.wajeezacademy.com/api/version
```

يردّ بجوابٍ عربيٍّ فيه: بصمةُ الالتزام العامل · الفرعُ · البيئةُ · **ووقتُ
البناء** · **ومصدرُ البصمة** · **وتسميةُ اللقطة المنشورة وهل هي من الالتزام
نفسِه**.

| ما تراه | ما يعنيه |
|---|---|
| الالتزامُ ليس آخرَ ما دفعتَه | النشرُ لم يكتمل، أو Varnish يقدّم قديما |
| «متطابقان: **لا**» | **اللقطةُ من التزامٍ آخر** — أي أنّ `catalog:publish` لم يعمل في آخر نشرة (القسم ٢) |
| «متطابقان: **نعم**» | الشيفرةُ واللقطةُ من التزامٍ واحد — النشرةُ اكتملت |
| **«الالتزام: null» و«مصدر_البصمة: مجهول»** | **البناءُ العاملُ بلا ختم**: `npm run build` لم يُشغَّل (فخطّافُ `prebuild` لم يجرِ)، أو أنّ الملفّات نُسخت نسخا بلا بناء. وحينها لا `‎/api/version` ولا غيرُه يعرف أيَّ نسخةٍ تعمل |
| «وقت_البناء» قديمٌ بأيّام | **النشرةُ لم تصل** — وهذا دليلٌ قاطعٌ حتّى لو جُهل الالتزام |
| لا يفتح أصلا | عمليّةُ Node متوقّفة |

### من أين تأتي البصمة

كان المصدرُ متغيّرا اسمُه `VERCEL_GIT_COMMIT_SHA` وحدَه. **وعلى Cloudways لا
وجودَ له**، فكان الجوابُ على الإنتاج الحيّ: «الالتزام: null · البيئة: محلية» —
امتناعٌ صادقٌ عن سؤالٍ صار أعمى، فلا يُعرف هل وصلت النشرةُ أم لا.

فالمصدرُ الآن ثلاثةٌ بترتيب الأسبقيّة (`server/build-stamp.ts`):

1. **بيئةُ المضيف** بأيّ اسمٍ أعلنها: `GIT_COMMIT_SHA` أو `VERCEL_GIT_COMMIT_SHA`
   أو `SOURCE_VERSION` أو `COMMIT_SHA`.
2. **ملفُّ `build-stamp.json`** يكتبه البناءُ نفسُه — يجري تلقائيّا قبل
   `npm run build` بخطّاف npm (`prebuild`)، ويقرأ التزامَه من نسخة Git
   الحاضرةِ على الخادم (والنشرُ على Cloudways سحبٌ من GitHub، فهي حاضرة).
3. لا شيء — فيقول «مجهول» ولا يخمّن.

> **ولا يُشغَّل `git` وقتَ التشغيل عمدا.** الخادمُ يخدم ما **بُني**، لا ما في
> القرص الآن: نسخةٌ سُحبت ولم يُعَد بناؤها تجعل `git rev-parse` يعلن التزاما لا
> يخدمه أحد — كذبةٌ في اللحظة التي تحتاج فيها الصدقَ أكثرَ ما تحتاجه.

> **والبصمةُ تدخل تسميةَ اللقطة كذلك** (`auto-<sha7>-<hash6>`)، وعليها يقوم
> «متطابقان». فبلا ختمٍ تخرج كلُّ لقطةٍ بالشكل الأعمى `auto-<hash12>` ويصير
> الجوابُ «لا يمكن الحكم» أبدا — وهو ما كان يقع على Cloudways.

> **وعرضُ هذا في شاشةٍ بندٌ مفتوح.** `‎/api/version` دقيقٌ **ولا يُستدعى من أيّ
> شاشةٍ في المنصّة**. فالسؤال «هل أرى الأحدث؟» لا جوابَ له إلّا بفتح هذا
> العنوان يدويّا.

## ٥) الدفع — Stripe

> الدليلُ العمليُّ في [`CONNECT_AR.md`](./CONNECT_AR.md).

- **عنوانُ الـwebhook:** `https://www.wajeezacademy.com/api/webhooks/payments/stripe`
  بحدث `checkout.session.completed`.
- المتغيّرات: `PAYMENT_DRIVER` · `PAYMENT_PUBLISHABLE_KEY` · `PAYMENT_SECRET_KEY` ·
  `PAYMENT_WEBHOOK_SECRET` — **لا `STRIPE_WEBHOOK_SECRET`، هذا الاسم لا يُقرأ**.
- `APP_URL` إلزاميّ: عليه تُبنى صفحةُ العودة بعد الدفع.
- القواعدُ الثابتة: لا بطاقاتٍ تُخزَّن · ورجوعُ المتصفّح ليس دليلَ دفع · والنجاحُ من
  الـwebhook وحدَه.
- **وفخٌّ يُذكر:** إن فُعِّل مزوّدٌ حقيقيٌّ **بلا مفتاحٍ سرّيّ**، يسقط النظامُ إلى
  المزوّد التجريبيِّ **صامتا** بينما تعرض الشاشةُ «صفحةُ دفعٍ آمنة».

## ٦) البريد

- **غيرُ موصولٍ اليوم** — ينتظر مفتاحَ Resend وحدَه.
- قبل الإرسال: `SPF` و`DKIM` و`DMARC` على النطاق، وإلّا وقعت الرسائلُ في المهملات.
- **وأثرُ غيابه ظاهرٌ للمستخدم:** شاشةُ ما بعد التسجيل تقول «أرسلنا رابطَ تحقّقٍ
  إلى بريدك» ولم يُرسَل شيء. (بندٌ في تقرير ٥ سبتمبر.)

### والمسارُ نفسُه سليمٌ ومُثبَت

المزوّدُ **Resend** (طلبُ السحب ١٦، دُمج في ٥ سبتمبر). وجُرّب المسارُ من طرفه إلى
طرفه على قاعدةٍ حقيقيّةٍ وواجهةِ Resend وهميّةٍ محلّيّة:

```
قناةُ البريد  : موصولة · مفتاح: موجود · من: no-reply@wajeezacademy.com
قبل الدورة    : queued
خبرُ الدورة   : حُوِّل ١ إشعارا: وصل ١، وسقط ٠
بعد الدورة    : sent · أُرسلت · لا خطأ
وواجهةُ Resend: POST /emails · من: أكاديمية وجيز <no-reply@wajeezacademy.com>
                إلى: عنوانُ المتعلّم · الموضوع: «وثّق بريدك»
```

**ومسارُ الفشل مُجرَّبٌ كذلك** بمفتاحٍ مرفوض:

```
خبرُ الدورة  : حُوِّل ١ إشعارا: وصل ٠، وسقط ١
بعد الدورة   : failed · «رفض Resend بيانات الدخول — راجع مفتاح API»
```

**فلا مجهولَ في الشيفرة — المجهولُ مفتاحُ المزوّد وحدَه.**

### ما يلزم للربط

| المتغيّر | ملاحظة |
|---|---|
| `RESEND_API_KEY` | **وجودُه وحدَه يفعّل القناة** · يبدأ بـ`re_` |
| `RESEND_FROM_NAME` | «أكاديمية وجيز» افتراضا |
| `RESEND_FROM_EMAIL` | `no-reply@wajeezacademy.com` افتراضا |

> **ونطاقُ المُرسِل هو ما يُوثَّق في Resend وتُضبط له SPF/DKIM — لا نطاقُ
> الموقع.** ورسالةٌ من نطاقٍ غيرِ موثَّقٍ يرفضها Resend نفسُه.

وتُضبَط إمّا في متغيّرات البيئة على Cloudways، **وإمّا من `/admin/integrations`
بلا نشرةٍ أصلا** — والمتغيّرُ يغلب الشاشةَ حين يوجد. **ولا يُرسَل مفتاحٌ في
محادثة.**

> **وفرقٌ تشغيليٌّ يُذكر:** Resend واجهةُ HTTPS لا SMTP. فالخادمُ يحتاج خروجا إلى
> `api.resend.com` على المنفذ ٤٤٣ — وهو مفتوحٌ افتراضا، **بخلاف منافذ SMTP التي
> تحجبها كثيرٌ من الاستضافات**. وهذا وحدَه سببٌ كافٍ لتفضيل Resend هنا.

## ٧) ما لا يعمل على Cloudways بلا عملٍ إضافيّ

| | الحال |
|---|---|
| **المُشغِّلُ الخلفيّ** | حقولُ الجدولة تُكتب ولا شيءَ ينفّذها: لا تذكيرَ يُرسَل، ولا محتوًى يُنشَر في وقته. **صار ممكنا على Cloudways ولم يُشغَّل بعد — والقسم ١٠ يشرح شرطَه** |
| **رفعُ الملفّات** | وثائقُ المتقدّمين تُخزَّن **داخلَ PostgreSQL** بسقف ٤ ميغابايت. ورفعُ التسجيلات والموادّ **لم يعمل يوما** |
| **بيئةُ التجريب** | لا وجودَ لها |
| **المراقبة** | لا متتبّعَ أخطاءٍ ولا فحصَ حياة |
| **النسخُ الاحتياطيّة** | `deploy/backup.sh` مصمَّمٌ وجيّد **ولم يُشغَّل في أيّ مكان**. وCloudways يوفّر نسخا — **والمطلوبُ إثباتُ الاستعادة لا وجودُ النسخة** |

## ١٠) المُشغِّلُ الخلفيّ — جاهزٌ، وشرطُه البريد

**العاملُ سليمٌ ومُجرَّب.** شُغّلت دورةٌ كاملةٌ على قاعدةٍ حقيقيّةٍ في ٥ سبتمبر،
فأبلغت وظائفُه الستُّ كلُّها صحيحا:

```
dispatch_notifications · session_reminders · cohort_status_sync
publish_scheduled_changes · cleanup_expired · enforce_retention
```

### ⚠️ ولا يُشغَّل قبل وصل قناة البريد — والسببُ مُثبَتٌ بالتجربة لا مُستنتَج

طابورُ الإشعارات يمتلئ منذ بداية المنصّة ولم يُفرَّغ قطّ. وجُرّب في ٥ سبتمبر ما
يحدث لو شُغّل العاملُ والقناةُ مغلقة — إشعارٌ في الطابور، ودورةٌ واحدة:

| | |
|---|---|
| قبل الدورة | `queued` |
| خبرُ الدورة | «حُوِّل ١ إشعارا: وصل ٠، وسقط ١ (قناةُ البريد أو المزوّد)» |
| بعد الدورة | **`failed`** · محاولات ١ · «لا مزوّدَ مربوطا لقناة email» |
| **ما زال في الطابور** | **صفر** |
| الدورةُ الثانية | «لا إشعارَ في الطابور» |

**ووظيفةُ الإرسال تختار `status: 'queued'` وحدَه.** فما صار `failed` **لا تنظر
إليه ثانيةً أبدا**.

> أي أنّ تشغيلَ العامل اليوم **يُحوّل الطابورَ كلَّه إلى «فاشل» في دورةٍ واحدة**:
> كلُّ رابطِ توثيقٍ معلَّق، وكلُّ دعوةِ موظّف، وكلُّ إيصالٍ — يُحرق دفعةً واحدة.
>
> والتعافي ممكنٌ لكنّه **يدويٌّ صفّا صفّا** من `/admin/notifications` بزرّ «إعادة
> المحاولة»، وبسقف ثلاثِ محاولاتٍ لكلّ صفّ.

### الترتيبُ الآمن

1. **وصلُ قناة البريد** — مفتاحُ Resend من `/admin/integrations`، والتأكّدُ برسالةٍ تجريبيّةٍ **تصل الوارد**.
2. **دورةٌ واحدةٌ للفحص** قبل الحلقة الدائمة: `WORKER_ENABLED=on npm run worker:once`
   — تعمل مرّةً وتخرج، ويُقرأ خبرُ كلّ وظيفةٍ قبل الالتزام بحلقة.
3. **ثمّ الحلقةُ الدائمة** عمليّةً ثانيةً إلى جانب الخادم:
   `WORKER_ENABLED=on npm run worker`
   وتُدار بمُشرِفٍ يعيد تشغيلَها عند السقوط (Supervisor على Cloudways أو ما
   يعادله) — **لا في الطرفيّة، فتموت بإغلاقها**.

> **وعلمُ التشغيل مقصود:** بلا `WORKER_ENABLED=on` يخرج العاملُ فورا معلنا أنّه
> غيرُ مفعَّل. فلا يعمل بالخطأ، ولا عمليّتان تتزاحمان على الطابور نفسِه.
